================================================================================
  PRINCIPAIS DESAFIOS IDENTIFICADOS
================================================================================

  1. DADOS PRE-EXISTENTES: ~40% dos testes precisam de fixtures no banco
     (produtos, projetos, atividades, contatos, usuarios, grupos, mensagens).
     Solucao: seed script ou API calls no beforeAll.

  2. SERVICOS EXTERNOS INDISPONIVEIS:
     - Ollama (AI Assistant) → 8 testes BLOQ
     - SMNA (Data Flow) → fallback mock cobre parcialmente
     - SMTP (OTP email) → 2 testes BLOQ

  3. TEMPO REAL: WebSocket e SSE sao dificeis de testar deterministicamente.
     Playwright suporta WebSocket via page.waitForEvent('websocket'),
     mas validar mensagens em tempo real requer 2 contextos simultaneos.

  4. NAO-DETERMINISMO: respostas da IA, dados do dashboard que mudam a cada
     dia, timestamps relativos — nao podem ter asserts de valor exato.

  5. UPLOADS: Playwright suporta file chooser, mas:
     - Mascara de input file estilizada pode complicar o seletor
     - Backend precisa aceitar uploads no ambiente de teste
     - Imagens enviadas precisam ser limpas apos o teste (cleanup)

  6. DRAG & DROP: Playwright suporta, mas libs como gantt-task-react e
     kanban podem usar eventos customizados (pointer vs mouse vs touch).
     Testes de drag sao notoriamente frageis.

  7. PERMISSOES: testar matriz de permissoes requer multiplos usuarios
     com diferentes niveis de acesso, o que torna o setup complexo.


================================================================================
  RECOMENDACOES
================================================================================

  1. PRIORIZAR testes [E2E] de esforco BAIXO primeiro — maior cobertura
     com menor custo (navegacao, asserts de existencia, CRUD basico).

  2. CRIAR FIXTURES via API: seed de dados no beforeAll usando as proprias
     APIs REST (criar produto, projeto, contato, etc.). Isso garante que os
     dados estao no formato esperado e isola os testes.

  3. USAR MOCKS para servicos externos: Playwright route intercept para
     simular respostas do Ollama, SMNA, etc. Isso desbloqueia varios [INF].

  4. SEPARAR SUITES por dominio:
     - auth.spec.ts        (login/logout/sessao)
     - navigation.spec.ts  (sidebar/topbar/links)
     - dashboard.spec.ts   (visao geral)
     - monitoring.spec.ts  (monitoramento)
     - products.spec.ts    (produtos & tasks)
     - projects.spec.ts    (projetos + kanban)
     - ai-assistant.spec.ts
     - reports.spec.ts
     - groups-users.spec.ts
     - chat.spec.ts
     - settings.spec.ts
     - contacts.spec.ts
     - help.spec.ts
     - cross-cutting.spec.ts

  5. NAO AUTOMATIZAR itens [MAN] e [VIS] via Playwright — usar testes
     manuais ou ferramentas de screenshot testing (Chromatic, Percy).

  6. TESTES DE REGRESSAO VISUAL com Playwright + screenshots para itens
     [VIS] — comparar screenshots antes/depois para detectar mudancas
     visuais nao intencionais.
